# 浏览器稳定性与平台恢复

首次操作 BOSS 网页前读取；异常时继续使用本轮记录，不能重新初始化恢复预算。

## 正常操作：先减少页面抖动

- 使用用户已登录的 Chrome 会话。先列出标签页，绑定一个已存在的 BOSS 标签页 ID；域名必须是 `zhipin.com` 或其子域，不能只做 URL 字符串包含判断。
- 本轮只操作这个标签页，所有导航、点击和读取串行执行；不并发抓取、不批量打开详情。不要关闭用户已有标签页、重启浏览器、清理登录数据或更改浏览器配置。
- 导航或点击后等待目标内容可见再继续，不把 BOSS 的持续网络连接当成未加载完成。优先使用工具支持的元素等待；无此能力时隔 2–3 秒重新读取，单次就绪检查最多 15 秒。超时先分类，不能直接刷新。
- 优先读取当前可见列表或详情区域；只有定位需要时才读取完整页面。滚动一屏后读取新增内容，不做无限滚动、紧密轮询或重复全页扫描。
- 元素缺失、旧元素失效或单次工具超时不代表网页崩溃。先重新读取当前状态并定位；页面仍正常时只重试未生效的只读动作，不 reload。
- 仅优化本 skill 时，不自动启动求职、投递或修改账户。规则优化不等于证明浏览器崩溃已修复。

## 本轮检查点

每个已完成步骤后保存必要信息，异常前已记录的内容不得清空：

```text
Task / Location / Keywords / Exclusions: 原任务与限制
Candidate pool / Analyzed / Applied: 岗位稳定标识、分析结果、明确成功证据
Browser / Tab ID / Last good URL: 工具会话、绑定标签页、最后正常 BOSS 页面
List checkpoint: 实际访问过的职位列表 URL、页面显示的城市/区县/关键词/筛选项
Message checkpoint: 仅在消息任务中记录实际访问过的消息列表 URL、目标会话的本地稳定标识和最后可见状态；不保存完整消息、Cookie、令牌或验证码
Last completed / Next action: 已完成步骤、下一步
Pending action: 尚未确认结果的发送、投递、上传或保存动作及目标
Recovery attempts: 本轮主动恢复次数，初始 0，上限 2
Crash count: 本轮工具明确报告或页面明确显示的崩溃次数，初始 0；新标签页、ID 变化或页面丢失不直接计为崩溃
Evidence: 时间、URL、页面可见状态或工具错误、已尝试动作及结果
```

在发送、投递、上传或保存前先记 `Pending action`；读到明确结果后再更新或清除。跨上下文续接也保留计数；页面短暂恢复、切换岗位、工具重连都不能重置。必要时在当前工作目录保存最小检查点，不保存 Cookie、令牌、验证码或完整聊天内容。

## 先分类，再恢复

| 分类 | 证据与处理 |
| --- | --- |
| `ELEMENT_OR_TOOL_ERROR` | 定位失效、单次读取超时；重新获取标签页状态一次。网页正常就重新定位，不刷新，不报告为闪退 |
| `TRANSIENT_PAGE_ERROR` | 就绪等待后仍白屏或有明确加载错误；进入有限恢复 |
| `MESSAGE_VIEW_BOOT_LOOP` | 已进入 BOSS 消息页，持续加载后在同一标签页变为空白/新页；未见登录、验证码、访问受限或明确崩溃证据。按消息视图专用恢复，不当作平台风控或已发送/未发送证据 |
| `UNEXPECTED_ROUTE_CHANGE` | 消息内容曾显示，但同一标签页随后跳到 BOSS 首页、简历页等其他有效页面；记录前后 URL 与时间。不要把有效页面说成白屏或崩溃，也不要推断跳转原因；在恢复预算内至多通过页面可见的消息入口重新进入一次并核对是否稳定 |
| `TAB_NAVIGATION_LOST` | 绑定页变成新标签页、空白页或 ID 消失；先重新列出标签页并核对原浏览器会话，不增加崩溃计数。即使只读操作期间同一标签 ID 从 BOSS 页面变成 `chrome://newtab/`、再变为 `about:blank`，也只记录观察到的地址变化；没有 CLI 调用时不能归因于 CLI，不能据此推断网站风控、验证码或页面崩溃 |
| `AGENT_CREATED_BLANK_TAB` | 本轮 CLI/Agent 操作后出现独立 `about:blank` 标签，且能确认它由本轮新建；这与原 BOSS 对话页变空白不同。停止待发送动作，只清理本轮新建的空白标签；无法确认归属就保留，不关闭用户标签，也不推断平台风控或发送结果 |
| `PAGE_CRASHED` | 工具明确报告页面崩溃或可见崩溃提示；增加 `Crash count`，进入有限恢复 |
| `CONNECTOR_DISCONNECTED` | 工具明确连接或权限失效；暂停并说明需要恢复实际使用的浏览器连接，不一律假定是 Chrome 插件 |
| `LOGIN_REQUIRED` | 明确登录页；保留页面，由用户登录 |
| `CAPTCHA_REQUIRED` / `PLATFORM_LIMIT` | 验证码、安全验证、操作频繁、访问受限或账号异常；进入 `PLATFORM_RISK_PAUSE`，立即停止自动操作，不刷新或换页绕过 |
| `RECOVERY_PAUSED` | 恢复预算耗尽、第二次明确崩溃，或当前状态不足以安全导航；保存检查点并停止自动恢复 |
| `BROWSER_POLICY_DENIED` | 浏览器工具明确拒绝页面读取、导航或诊断，且声明不得换途径完成同一动作；记录被拒绝的动作与理由，停止该动作，不改用原生窗口、命令行、CDP、另一浏览器或用户操作来绕过。只继续无需该动作的本地草稿和分析；缺少页面证据的结论保持待核实 |

证据不足时报告“读取失败/原因待核实”，不能把白屏直接归因于网站风控、内存不足、浏览器进程崩溃或连接断开。有明确证据表明用户关闭或改用该标签页时，不要抢回焦点或立即重开；不能仅凭出现新标签页就推断用户主动关闭。

## 有限恢复

1. 暂停操作队列，保存检查点；重新列出标签页并检查绑定页。旧工具句柄失效但标签页仍在时重新绑定，不导航。发现正常 BOSS 页面则复用；有多个时优先原绑定页，不轮流尝试所有页面。
2. 恢复预算只限制主动导航、reload 和替代页创建，不限制最后一次标签页清点、重新绑定和只读核对。即使预算耗尽，也先执行第 1 步；发现已正常的 BOSS 页就继续，不能仅凭计数直接要求用户打开网页。检查登录、验证和平台限制；这些状态直接暂停，不消耗重试去绕过。`Crash count >= 2` 或 `Recovery attempts >= 2` 时停止主动恢复。该上限适用于整轮任务，用户明确要求重新诊断后才可开始新一轮。
3. 第一次主动恢复只选一个动作：绑定 BOSS 页仍在且加载错误时 reload 一次；绑定页变空白或新标签页时，消息任务优先导航到 Message checkpoint 的实际消息列表 URL，其他任务优先导航到 List checkpoint 的实际列表 URL；其次才是最后正常 BOSS URL，无记录才用 `https://www.zhipin.com/`。这些动作均以浏览器工具允许为前提；遇到 `BROWSER_POLICY_DENIED` 立即停止，不把拒绝当成普通超时。每次 reload、恢复导航或创建替代页前增加 `Recovery attempts`，即使工具超时也计数。
4. 绑定页确实消失且没有可复用 BOSS 页时，最多创建一个替代页；首次任务完全没有 BOSS 页时也允许创建一个工作页。不得导航覆盖用户正在使用的非 BOSS 页面或来源不明的空白页；不得关闭再重建原页。创建后等待并读取，不连续建页。
5. 首次恢复仍失败，只有存在不同、合理的恢复动作时才进行第二次尝试；先间隔至少 5 秒，再用当前任务的已记录列表 URL恢复；若原页反复丢失且尚未创建过替代页，可以在同一 Chrome 会话创建唯一替代页并直接打开该 URL，此动作计入第二次尝试。不得重复同一个无效动作。已无不同动作时提前暂停，不必凑满预算。
6. 每次恢复后等待就绪并读取 URL、标题、可见关键内容。正常内容出现后，间隔至少 3 秒再读取一次，确认同一标签页与目标内容仍可用，才结束恢复；此时不清零计数。仍失败或再次崩溃则按预算暂停，禁止自动重启浏览器或循环刷新。

## 消息视图专用恢复

仅在可观察到“消息页持续加载 → 同一标签页空白/新页”的完整序列时使用。它与通用恢复共用 `Recovery attempts`；不因成功回到消息列表而重置预算。

若对话已显示、随后跳到另一个有效 BOSS 页面，按 `UNEXPECTED_ROUTE_CHANGE` 处理：先保留当前可读页面和检查点；工具允许时，只从当前页面可见的消息入口重进一次，计入恢复预算。再次跳走就停止消息页恢复。若工具明确拒绝操作，立即按 `BROWSER_POLICY_DENIED` 停止，不用替代控制方式重试。

1. 立即暂停消息读取和任何待发送动作，记录当前 URL、标题、可见加载/空白状态、Message checkpoint 与 `Pending action`。该症状本身不说明消息已发送、未发送、已读或未读。
2. 重新清点并绑定原 BOSS 标签页。存在正常 BOSS 页面时优先复用；原消息页为空白且有实际 Message checkpoint 时，只导航回该消息列表 URL，计一次主动恢复。没有该检查点时不要猜测消息路径、拼接会话 ID 或把职位列表当作消息恢复入口。
3. 消息列表连续两次可读（间隔至少 3 秒）后，才可通过可见的目标会话条目重新进入一次；只读取对话，不点击输入框、发送、上传或任何写入控件。没有清晰目标条目时，保持在消息列表并报告待核实。
4. 重新进入后再次出现同一加载→空白序列，或消息列表本身无法稳定恢复时，标记 `MESSAGE_VIEW_UNAVAILABLE` 并停止本轮消息页自动恢复。不得 reload 目标对话、反复开新标签、切换账号/网络、调用替代接口，或要求用户重复发送。
5. `Pending action` 非空时，仅在恢复后的消息列表或会话页出现明确平台回执后更新结果；否则标为“发送结果待核实”。消息视图不可用不阻止无关的只读搜岗，但阻止该会话的发送、跟进和状态推断。

## 恢复后的任务续接

- 列表页恢复后核对页面显示的城市、区县、关键词和筛选项；缺失时使用可见控件自行补回，再读取列表确认。比如原任务为“肇庆·端州区”，由 Agent 选回肇庆和端州区，不要求用户手动定位到指定列表。不要猜测城市代码或拼接未经验证的 URL 参数。
- 消息列表恢复后仅核对目标会话是否仍可见和最后可见状态；不能因消息内容未加载推断对方已读、未读、回复或未回复。若进入目标会话触发 `MESSAGE_VIEW_UNAVAILABLE`，保留消息列表检查点，不再自动打开该会话。
- 正常页面上的筛选属于原任务的只读续接，不算故障恢复；筛选再次导致异常时仍沿用本轮预算，不借此循环导航。
- 本轮确实没有发起任何写操作且 `Pending action` 为空时，没有“待核实的本轮投递”，不得以无法核对投递状态为由阻断只读找岗。既有投递历史未知时单独标记，投递前再核对；历史缺失不能写成“从未投递”。

- 先按公司、岗位和页面稳定标识核对当前位置，保留候选池、排除项、已分析和已投记录，只继续剩余只读工作，不询问“是否继续”。
- 如有 `Pending action`，先查看沟通记录、投递状态或保存内容。明确成功就记完成，明确未生效才按原授权继续；无法确认则标为“结果待核实”，停止该写操作，不自动重发或重复提交。其他独立只读工作可以继续。
- 页面恢复不扩大授权。验证码由用户处理，外部写入继续遵守主 skill 的授权条件。

## 暂停报告

简短报告实际观察到的状态、已尝试的动作与次数、已保留的进度，以及需要用户处理的最小事项。禁止套用“请打开肇庆·端州区列表页，回复已打开”。登录只请登录、连接失效只请恢复连接；恢复预算耗尽且最后一次清点仍无可用页面时，如实说明自动恢复已停止和页面状态，不把预算耗尽说成登录失效。`MESSAGE_VIEW_UNAVAILABLE` 只报告“消息页加载后转空白，未见验证码/平台限制证据”，不要臆测根因或要求用户重发。仅在必须人工处理时提出对应动作，不要求用户重做地区筛选或发送固定口令。用户完成处理后重新读取页面状态，自行重建列表。平台验证或明确断连时可以立即报告，不必用完恢复预算。

只按证据描述：单次恢复成功只能说“本次页面已恢复”；未复现闪退时不能声称“闪退已修复”。有结果不明的写入必须明确列出，不得笼统声称未发生任何投递或发送。
